# Decisions, Caveats & Known Issues

Durable memory across Claude Code sessions. Read this before proposing architecture or
diagnosing behaviour that looks like a bug.

**Rules for writing here — this file must stay scannable:**
- One row per entry. No prose paragraphs, no code blocks. Cite `file.py:line` instead of restating code.
- Record only what the code and git history cannot tell you: *why* a choice was made, what was
  rejected, what is deliberately unfinished. Never document what a function does.
- Add a row when you decide something non-obvious, discover a landmine, or find earlier
  analysis was wrong. Do not add a row for routine work.
- **Delete rows that are resolved or obsolete.** Growth is the failure mode. Update in place
  rather than appending a correction.
- New IDs continue the sequence; never renumber.

## Decisions

| ID | Date | Decision | Why |
|---|---|---|---|
| D-01 | 2026-08-07 | Legacy modernization ships as **one new product ID** (`modernization`, `kind=WORKFLOW`, `invoke=None`), not an evolution of `migration-execute`. | Product IDs are persisted in `api_keys.scopes`, `api_key_cost_log.agent_name`, `api_key_agent_llm_config.agent_name` (UNIQUE). `registry.py:20-25` says they were chosen to avoid data migration. `swarm` is the precedent for a workflow product with its own dispatch. |
| D-02 | 2026-08-07 | Modernization v1 is **language-agnostic substrate first**; per-pair specialization (Delphi→.NET first) comes after. | User decision. The substrate is the risky part; analyzers are per-language work that doesn't generalize. |
| D-03 | 2026-08-07 | Durable execution = **claim-and-lease on a table row**. No Celery / RQ / Redis / Temporal. | ~300 lines, zero new infrastructure. The repo has no ops story for a broker. |
| D-04 | 2026-08-07 | Dependency graphs come from **deterministic parsers**, never from the LLM. LLM classification is allowed only as a fallback, and must be recorded in `classification_source`. | An LLM graph is silently wrong in a way that corrupts conversion *order*, which corrupts every later file. Invisible until file 300. |
| D-05 | 2026-08-07 | **No compiling or subprocess execution on the API host.** v1 validates structurally in-process; real builds go to the customer's CI via a branch + PR (`autofix_pr.py:90-110` is the template). | Building LLM-generated code from customer source is arbitrary code execution. Also: real builds need the real SDK and package restore, which don't belong on a FastAPI host. |
| D-06 | 2026-08-07 | Prompt-cache breakpoint sits on the **system block only** (`llm_gateway._cacheable_system`). Tools render before system, so one breakpoint covers both. | The per-request artifact stays in `messages`, after the breakpoint, so it can never invalidate the prefix. |
| D-07 | 2026-08-07 | `PRAGMA foreign_keys=ON` **deliberately not enabled** despite WAL + `busy_timeout` being turned on. | `reports`/`approvals` FK to `reviews(id)`; there is no test suite and possibly orphan rows, so enforcement could start raising `IntegrityError` in live paths. Enable only alongside an orphan audit. |
| D-08 | 2026-08-07 | Code Review guards belong **inside `CodeReviewAgent.review_code`**, not in `orchestrator.review_code`. | Four of five call paths bypass the orchestrator — see C-08. The agent method is the only common seam. |
| D-09 | 2026-08-07 | **Do not introduce pytest.** New tests follow `scripts/smoke_products.py`: plain script, `check()`/`section()`, exit 0/1, `TestClient`, `llm_gateway.call_tool` monkeypatched. | Matches the repo's existing (deliberate) no-test-framework convention. 163 checks already run this way. |
| D-10 | 2026-08-07 | The deterministic gate is a **floor, not a replacement**: the result is the stricter of (arithmetic over findings, model's own gate). `finding_gate.reconcile_gate`. | Makes the change incapable of weakening any gate issued today — important because these block releases, and `full_review`'s aggregate gate is computed from them. The model can see context a severity tally can't. `model_gate_status` is preserved so the disagreement rate is measurable. |
| D-11 | 2026-08-07 | `risk_score` is **floored to match the gate** (Red≥70, Amber≥40), not recomputed. | A gate and score that disagree ("Red, risk 5") is the signature of a partial response. Recomputing it outright would change `calculate_overall_risk` for every `full` review, for less benefit than fixing the incoherence. |
| D-12 | 2026-08-07 | The four workflows that bypass the orchestrator were **not** re-routed through `orchestrator.review_code`, despite the original plan. | `review_pr.py`/`autofix_pr.py` write their own `save_review` with PR-specific `project_name`; routing them through the orchestrator would double-persist and change that semantics. Putting the guards in the agent method (D-08) already reaches all five paths, which was the actual goal. |
| D-13 | 2026-08-07 | Untrusted-content wrapping in `_resolve` defaults **on**. Transforming endpoints pass `untrusted_mode="transform"`, which wraps with different wording, rather than opting out. | Default-secure. The transform wording tells the model the markers are packaging to drop; skipping the wrapper entirely left the sharpest path open — planted text in a fetched source file steering generated code a customer may commit. |
| D-14 | 2026-08-07 | Chunks are packed using the **character estimate**, not `llm_gateway.count_tokens`. | Packing needs a number per candidate split; an API round trip each would cost more than it saves. `count_tokens` stays available for callers that need precision. Being ~10% off changes packing efficiency, never correctness. |
| D-15 | 2026-08-07 | Evidence is verified against the **whole original artifact**, and line correction is **off for diffs**. | A chunk is a substring of the artifact, so presence still holds and the recovered position is absolute. In a diff the model's `line_start` comes from the `@@` header and means a line in the *file*; a position recovered from diff text means a line in the *diff*. "Correcting" one to the other replaces a right answer with a wrong one. |
| D-16 | 2026-08-07 | Pre-existing findings **still count toward the gate**; only explicitly waived ones are excluded. | Excluding everything seen before would let a codebase with a hundred existing Criticals report Green — worse than a gate that takes work to turn green. They are labelled `is_new: false` so callers can still say "3 new, 41 pre-existing". |
| D-17 | 2026-08-07 | Failed calls are now metered with **`billable=0`** and `status="failed"`, not charged. | Resolves C-04 without a pricing change. A truncation fires after the provider generated (and billed us for) thousands of tokens; those were recorded nowhere, so repeated failures could overrun a cap invisibly. Making them *billable* is still a pricing decision. |
| D-18 | 2026-08-07 | Budget reservations size from `RESERVATION_MAX_TOKENS` (32000) × expected calls per product, not `config.MAX_TOKENS` (16000). | Resolves C-03. Architecture asks for the top tier and `full` is 7 calls under one guard, so the old reservation bounded roughly a fourteenth of what a `full` run could spend. The constant must move whenever any agent's budget goes above it — `unit_converter.CONVERSION_MAX_TOKENS` and `base_agent`'s architecture call both sit exactly at it. |
| D-19 | 2026-08-07 | The modernization schema (6 tables) lives in `services/modernization/store.py`, called from `database.init_db()` via a lazy import, rather than in `database.py`. | `database.py` is 2200 lines and read by everything; these tables are read by one subsystem. Tables are still created in exactly one place at startup, so the convention that matters is intact. |
| D-20 | 2026-08-07 | Modernization meters **per converted file** — one `guarded_call` per unit — which is the opposite of the workflow rule in `agent_guard`'s docstring. | A run is not one request: it is hundreds, over hours, pausable. Per-unit gives real per-file cost, budget accrual as it goes, and a natural stop at the cap. One guard around the whole run would only discover an overspend at the end. `_EXPECTED_CALLS_BY_PRODUCT["modernization"]=1` because each guard really is one call. |
| D-21 | 2026-08-07 | Cycles are broken **deterministically** (intra-SCC edges dropped in `graph.build`) and recorded as a **non-blocking** checkpoint, not a blocking one. | Nothing in an SCC could ever become `ready` otherwise — the run would deadlock rather than convert. Blocking on each cycle would stall every legacy codebase at file zero, since legacy code is full of them. The blocking `plan_approval` gate already puts them in front of a human before any spend. |
| D-22 | 2026-08-07 | `repo_ingest.safe_relpath` rejects **any** `..` segment, including ones that normalize back inside the root. | "Resolves safely" is a much weaker guarantee than "isn't there", and a source archive has no legitimate reason to contain one. Output paths are derived from input paths, so this is a real traversal primitive rather than a theoretical one. |
| D-23 | 2026-08-07 | An unresolved symbol is a **warn**, not a **fail**; a reintroduced secret is a **terminal** failure with no retry. | A legitimate forward reference inside a converted cycle is indistinguishable from a real unresolved symbol, so failing those makes cyclic codebases unconvertible. A secret is a behaviour, not a transient — retrying spends the same tokens for the same answer, and `autofix_pr` already refuses to commit one. |
| D-24 | 2026-08-07 | `database.save_review` now stamps `finding["id"]` onto each finding **before** serializing `result_json`. | Resolves C-11. Findings got a row id at save time but it never travelled back, so a client could see a finding and had nothing to name in `PATCH /api/v1/findings/{id}` — which is why waiving was API-only. Additive; `result_json` gains a key. |
| D-25 | 2026-08-07 | Chunk-count-aware reservations use a **contextvar** (`agent_guard.expect_calls`), sized from `code_chunker.estimate_chunks` at the route. | Resolves C-17. The real chunk count is only known deep inside the agent, after splitting, while the guard is taken at the route — threading it back up would mean every caller of every chunkable agent learning about reservations. Division-based estimate, not a real split: being a chunk out changes when a marginal caller sees a 402, never whether the review is correct. |
| D-26 | 2026-08-10 | `full` gains three **opt-in stages** (STRIDE / VAPT / sensitive-data) rather than splitting into a second `full-plus` product. Title becomes "Core SDLC Review"; **the id stays `full`**. | A second id means new `plan_products` rows, updating every existing plan or customers silently lose access, and two `reviews.review_type` values splitting history — `registry.py:20-25`'s reason for never re-iding. `Product.title` is display-only, so the honest name costs a string and no migration. Same shape as D-01. |
| D-27 | 2026-08-10 | The opt-in stages gate on **flag AND artifact** (`full_review.plan_steps`), and `run()` dispatches off the computed plan (`will_run`) rather than re-deriving each condition. | The plan drives the progress bar, the job's `total_steps` and the budget reservation; when `run()` re-derived the same conditions independently, the two could disagree. Asking for VAPT with no code is a no-op rather than an error — the UI warns, the API stays permissive. |
| D-28 | 2026-08-10 | `full` reserves budget via `agent_guard.expect_calls(count_steps(plan_steps(...)))` at both routes, not the fixed `_EXPECTED_CALLS_BY_PRODUCT["full"] = 7`. | With toggles the real count is 5-10 and only the plan knows which. Reuses D-25's contextvar rather than inventing a second mechanism. |
| D-29 | 2026-08-10 | `full`'s result and persisted review carry **`steps_not_run`**, and the UI renders those as struck-through "not run" pills. | A Green over five of eight possible checks renders identically to a Green over all eight. The gate was already only as broad as the reviews behind it; this is the first time a reader can see how broad that was. Persisted, not just returned, so the omission survives into history. |
| D-30 | 2026-08-10 | `shared.governance_review` returns findings **flattened onto `findings`** and both callers copy it, plus `gate_status`/`risk_score`, to the top level of the result they persist. | They lived only under `result["governance_review"]`, and `load_findings_from_reviews` reads `result["findings"]` while `save_review` derives its counts from the same key — so a scaffold whose auto-review found Criticals reached the release gate as zero findings and showed Green on the dashboard. `strictest_gate` combines the two agents' gates with the deterministic floor, per D-10. |
| D-32 | 2026-08-10 | `:root` sets **`color-scheme: dark`** and `select option` gets explicit opaque colours (`styles.css:22,890`); no `<select>` may use a translucent `background`. | A `<select>`'s dropdown popup is a native widget — it does not inherit a translucent background, so it painted light while options inherited `--text` (`#e2e8f0`): light-on-white, unreadable. `.sidebar-project select` hit this via `var(--bg-input, rgba(255,255,255,.04))`, and **`--bg-input` is not defined anywhere** — the fallback was always what applied. |
| D-31 | 2026-08-10 | `reports` gains **`project_id`**, stamped by `save_report` from the request context, and `GET /api/reports` lists them. | Reports carried only a free-text `project_name`, and `get_report` scoped through `reports.review_id` — which both writers set to `None` (`full_review.py`, `standalone_report.py`), so **every report was a 404 for anyone but a super admin**. Mirrors `reviews.project_id` exactly; the review fallback stays for rows written before the column. |
| D-34 | 2026-08-11 | An admin-selected **platform LLM connection** is a new precedence rung, resolved inside `llm_gateway.call_tool` via `platform_default()` / `resolve_override()` — not pushed through `with_override()`. | `agent_guard.guarded_call` wraps every call in `with_override(override)`, which for a UI caller sets the contextvar to **None** and would shadow any outer value. Resolving at call time is also what makes one setting reach every surface (UI review forms, Agent Hub, Swarm, workflows, jobs, v1) instead of needing a change per route. Precedence: per-request > per-agent key > key global > platform connection > `.env`. |
| D-35 | 2026-08-11 | The active connection's id lives in **`platform_settings`** (`active_llm_connection_id`), not an `is_active` column on `llm_connections`. | The KV table and its `get/set_platform_setting` helpers already exist and already carry a platform-wide toggle (cost optimization). A column would need a partial unique index to enforce "exactly one" and a two-statement update to move it; a single KV write is atomic by construction. `delete_llm_connection` clears the key so a deleted connection can't stay selected as a dangling id. |
| D-36 | 2026-08-11 | `agent_guard` labels the ledger from the **resolved** LLM (`effective_llm`) but decides `billable` from the **caller's** override only. | They answer different questions. "Which model served this?" must follow the platform connection or every UI call is recorded as Claude when it wasn't. "Whose account paid?" must not: a platform connection is our endpoint and our bill, so it stays billable — folding it in would silently stop project budgets accruing the moment an admin selected one, with nothing in the logs to explain it. |
| D-37 | 2026-08-11 | `call_tool` resolves `max_tokens` once for both providers, and a connection's configured `max_tokens` is a **ceiling that clamps** the agent's request, not a default it overrides (`llm_gateway.py:406-424`). | The two paths disagreed: Anthropic used `config.MAX_TOKENS`, OpenAI a hardcoded 4096, so an agent naming no budget got half the room on OmniRoute and surfaced `LLMTruncatedResponseError` rather than a shorter answer. The clamp (added with D-38) exists because agents now ask for 32000, above what several OpenAI-compatible models accept as an output cap at all (gpt-4o: 16384) — unclamped that is a non-retryable provider 400, clamped it is at worst a truncation that says so. Clamping is logged. Only affects requests *above* a configured ceiling; every other case resolves exactly as before. |
| D-38 | 2026-08-11 | Output budgets roughly **doubled across every agent** (floor `config.MAX_TOKENS` 8000→16000, top tier 16000→32000, VAPT/security 14000→28000, GxP generate 12000/14000→24000/28000, governance prose 4096→8000), and `LLM_TIMEOUT_SECONDS` 360→900 in the same change. | Truncation is the expensive failure here: the response is discarded, the tokens are still billed (D-17), and the budget is what caused it. Headroom above the longest legitimate response costs nothing — the provider bills tokens generated, not tokens allowed. The timeout is not separable: 32000 tokens at the 50-80 tok/s a Sonnet-class model sustains is 400-640s, so leaving it at 360 would have converted the new budgets into timeouts plus two retries. Still far below the model's real 128000 ceiling. |

| D-40 | 2026-08-12 | The legacy `/api/release-gate` now goes through `orchestrator.run_release_gate` → `workflows/release_gate.run` instead of calling `orchestrator.gate_agent.evaluate_gate` inline. `run()` gained a `findings=` parameter to keep the pasted-findings input shape. | The inline version persisted **nothing**, so the Release Gate page — the platform's most consequential output — produced a verdict that never reached History, could never be picked by the Governance Report's review picker, and never entered the approval queue. `/api/v1/agents/release-gate` for the same product always persisted: one product, two behaviours depending on the door. Not a D-12 case — D-12 kept bypasses that write their *own* review rows; this one wrote none. |
| D-41 | 2026-08-12 | `full`'s stages now receive a **digest of earlier stages' findings** (`full_review._stage_context`, capped at 12, highest severity first) rather than the caller's raw context alone. | Every stage got the same string and its own artifact, so no stage ever saw another's output and the eight agents met for the first time at the gate — a batch of independent reviews wearing one name. A digest rather than the findings themselves, so a later stage still reviews its own artifact. Verified against the live API: the Code Review stage's summary now reads "All findings directly confirm the earlier-stage requirements review…". Cache-safe — context rides in the user message, after the D-06 breakpoint. |
| D-42 | 2026-08-12 | Read-scoping lives in **`backend/scope.py`**, not `main.py`. `visible_project_ids(reader, request)` moved there verbatim; `visible_from_caller(caller)` added for routers holding a `v1_agents.get_caller` dict. | The rule was reachable only by routes defined in `main.py`, so every other router either reinvented it (`modernization._visible_project_ids`) or skipped it — `routes/approvals.py` listed every approval in the deployment to anyone holding a token. Sits beside `context.py` for the same reason: the routers import it and `main` imports the routers. |
| D-43 | 2026-08-12 | A swarm whose **required agent errored** returns AMBER, never GREEN (`swarm_service._aggregate`). | An errored agent is excluded from `scores` and from `agents_failed`, so `required_failed` stayed empty and the swarm could certify clean over a mandatory check that never ran. AMBER rather than BLOCKED keeps the documented promise that "one agent crashing never blocks the gate" — what it may no longer do is come back clean. |
| D-44 | 2026-08-12 | `findings` gained a read side (`GET /api/v1/findings`, `database.list_findings`/`count_findings`) and a Findings page in the SPA. `PATCH /api/v1/findings/{id}` now checks project ownership. | The lifecycle had a write verb and no way to reach what it acted on: waiving was possible only from the review-detail modal of the review that produced the finding, so "what is still open in this project" was unanswerable. | D-45 | 2026-08-14 | Modernization stages are **rows in `modernization_units` with a `kind`**, not a second table and not a second execution model. `stages.py` holds the order as data; `runner.convert_run` is a driver over it. | Claim-and-lease, lease recovery, per-unit metering and the one-transaction checkpoint are the most subtle 200 lines in the subsystem and the most heavily smoke-tested. A `modernization_stages` table would mean a second copy of all of it. `parent_unit_id` already existed for this and nothing wrote it. |
| D-46 | 2026-08-14 | **One unit is at most one LLM call.** A stage needing two calls per row becomes two stages. | It is what keeps D-20 literally true and `agent_guard._EXPECTED_CALLS_BY_PRODUCT["modernization"] = 1` correct without touching the guard. Break it and every reservation in the product is wrong by an unknown factor. |
| D-47 | 2026-08-14 | The conversion unit is a **component** (N source files → M target files), not a file. Members go to a new `rolled_up` status, flipped to `converted` by `complete_unit` in the same transaction as the component. | 1:1 is wrong for the common legacy shapes: a PHP page-script is markup + query + logic and must become three files; thirty page-scripts sharing `header.php` must become *one* layout. `rolled_up` is deliberately not `converted` — otherwise "417 of 523 files" would become true the moment the plan was approved. |
| D-48 | 2026-08-14 | **Two spend gates.** `discovery_approval` quotes a bounded assessment; `plan_approval` quotes the conversion from measured input and a provable ceiling. `agent_guard.estimate_cost()` made public. | The old single gate said "Nothing has been spent yet" and carried no number, because pricing a conversion requires understanding the codebase and that costs money. | D-49 | 2026-08-14 | The converter returns `files[].filename` (bare) plus optional `subdir`; the directory comes from the component and is joined in **Python**. | File 1 wrote `Api/Controllers/X.cs` and file 200 wrote `src/Api/Controllers/X.cs` and nothing compared them. Repairing a path is right at *design* time (once, pre-spend, printed on a plan a human approves) and wrong at conversion time, where it would be invisible. |
| D-50 | 2026-08-14 | Scaffolding (`.sln`, `.csproj`, `Program.cs`, `appsettings.json`) is **deterministic — zero LLM calls** — and versions are pinned constants. | A model asked for a `.csproj` produces package versions that look right and do not exist. The package set follows from charter decisions already taken, so deriving it is a lookup. The stage still owns a row, for resumability and metering symmetry. |
| D-51 | 2026-08-14 | The comprehension digest, architecture map and language playbook are rendered **once at plan approval** into `modernization_runs.system_addendum` and concatenated verbatim by `system_for()`. | Re-deriving them per unit from a dict `json.loads` rebuilt could produce a different key order and silently cost full price on all 500 calls, with nothing in the logs but `cache_read=0`. Same argument `charter.render` already makes. Capped at 60k chars: a prefix that grows with the codebase is a prefix that is never cached. |
| D-52 | 2026-08-14 | The PHP→.NET playbook lives in **Python constants** (`services/modernization/playbooks/`), scoped per run from the run's own inventory. | D-53 | 2026-08-14 | `analyzers/php.py` runs tree-sitter when available and a **real** regex analyzer when not — never falling through to `generic`. `provides` carries path spellings as well as names. | Falling through to `generic` restores the zero-edge defect the module exists to remove, so a parse failure must degrade precision (recorded in `source`/`confidence`) rather than availability. | D-54 | 2026-08-14 | `.inc` is **not** registered for PHP; PHP `.inc` files go through the per-run extension override. | `pascal.py` owns `.inc`, `register()` is last-write-wins over an alphabetical import, and taking it would silently break every Delphi run in the deployment. |
| D-55 | 2026-08-14 | Hazards (`eval`, variable variables, dynamic includes, `extract`, `unserialize` on request data, shell-out) are enforced in **three** layers: prompt rule, `// MIGRATION-BLOCKED:` marker, and a Tier-0 check that **fails** output carrying neither the marker nor a `manual_followup` entry. `validation.BLOCKING_HAZARDS` filters inside the check, not at the caller. | A flag nobody enforces is decoration. | D-56 | 2026-08-14 | `insert_units` **derives** `dependents` from `depends_on` when a caller does not supply it. | `_promote_ready` now navigates the reverse index to decide who may have become ready, so it stopped being informational. | D-57 | 2026-08-14 | Charter suggestions are **deterministic — no LLM, ever** (`services/modernization/advice/`), derived from `playbooks.aggregate_facts` + `evidence.summarize`. | The charter is set *before* `discovery_approval` (it is `set_charter` that raises it), so a model call here would be the run's first spend with nothing approved and the screen above it promising analysis is free. The smoke suite asserts `call_log` is unchanged across the whole path — that check *is* the decision. |
| D-58 | 2026-08-14 | `charter.required_for(observed)` may **only remove** a field from the required set, never add one. | D-59 | 2026-08-14 | Charter `help` text names **no framework**; concrete examples come from `advice`, keyed by language pair. `dependency_injection` renamed to `composition`, with `LEGACY_KEYS` folding the old key in `canonical()`. | Every help string used to be a .NET example, so a COBOL→Java user read twelve fields written for someone else — and DI is not a stack-neutral concept at all (meaningless for Go, Python, Elixir).
